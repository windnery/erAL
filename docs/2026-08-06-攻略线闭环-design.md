# erAL 攻略线闭环 设计文档

> 日期：2026-08-06
> 状态：已确认（用户批准整体设计）
> 关联计划：`docs/plans/2026-08-06-M0~M4-*.md`

## 1. 背景

erAL 是一款舰B同人游戏（Python + pywebview + HTML/JS 前端），玩法大量移植自 EraTW（eratw4.980）。当前为 MVP：

- **已完成**：24h 时间系统、地图移动、NPC 作息调度、指令注册框架、source/palam/juel/abl 数值管线、秘书舰系统、日终结算、4 只可攻略舰娘、前端主循环。
- **核心问题**：玩家没有"目标"。好感只是数字，`relationship`（陌生→友好→喜欢→爱→誓约）五级陷落阶段没有任何推进事件，游戏循环（工作→互动→睡觉）单调且不可持续。
- **致命缺陷**：存档/读档按钮是空实现，游戏无法持久化。

**方向确认（用户）**：
- 日常+恋爱攻略为主；调教系统是重头戏但暂缓，且自创玩法不照搬 tw。
- 当前阶段目标：让游戏"能完整玩下去"。
- 投入：每周 10-20 小时，按 2-4 周一里程碑。

## 2. 目标与成功标准

构建一条从"陌生"到"誓约"的完整攻略线：

1. 玩家可以随时存档/读档，游戏进度可持久化。
2. 玩家可以与舰娘约会（邀请→同行→地点互动→结束），约会途中解锁专属指令。
3. 玩家可以通过工作赚钱、在商店购买礼物（不知火）和皮肤（明石），送礼推进好感。
4. 好感/信赖达到阈值触发 relationship 推进事件（友好→喜欢→爱），可告白，最终可誓约。
5. 誓约后解锁专属口上、特权与皮肤，形成"奖励感"。
6. 明石、不知火作为商店驻点 NPC 加入（暂不可攻略）。

**成功标准**：新玩家可以在不修改代码的情况下，通过正常游玩完成"第 1 天→誓约"的全流程，且中途任意存档点读档后状态一致。

## 4. 跨里程碑接口约定

以下接口在各计划中必须保持一致（防止计划间脱节）：

### 4.1 SaveManager（M0 引入）

新增 `game_engine/managers/SaveManager.py`，负责世界状态的序列化：

```
SaveManager(sav_dir: Path)
  save_game(world, slot: int) -> dict        # 序列化+落盘，返回 meta 供前端显示
  load_game(world, slot: int) -> str | None  # 读档并还原 world，出错返回错误信息
  get_save_list() -> list[dict]              # 各槽位 meta（含空槽位标记）
  serialize_world(world) -> dict             # 纯序列化（可单测）
  deserialize_world(world, data: dict)       # 纯反序列化（可单测）
```

- 存档位置：`sav/slot_{n}.json`（n = 1/2/3），`.gitignore` 加入 `sav/`。
- 文件结构：`{"version": 1, "meta": {...}, "data": {...}}`。
- **存 delta 不存全量**：静态数据（lines/schedule/talent 初始值/地图/商品表）始终从 `data/` JSON 重建；存档只存运行时字段。
- **运行时字段清单**（M0 锁定，后续里程碑只增不改）：
  - player：`location`、`base`、`money`、`wake_time`、`abl`、`exp`、`juel`、`palam`、`talent`
  - shipgirl：`location`、`base`、`favor`、`trust`、`abl`、`exp`、`juel`、`palam`、`cflag`
  - world：`day`、`hour`、`minute`、`works`、`works_done`、`menu_active`、`secretary_ship_id`、`version`
  - `palam_lv` 为派生值，读档后调 `update_palam_level()` 重算，不存储。
- 反序列化流程：从 `data/` 重建 Player/ShipGirl 对象 → 覆盖运行时字段 → 重算派生值 → 恢复 `secretary_ship` 引用 → 一致性检查。

### 4.2 驻点机制（M2 引入）

舰娘 JSON 数据新增可选字段 `"station": {"region": "...", "node": "..."}`：

- `NpcManager.update_positions()` 调度优先级改为：**驻点 > 秘书舰跟随 > 睡觉 > 工作 > 自由行动**。
- 有 `station` 的舰娘：永远在驻点，`sleeping`/`working` flag 恒为 False，不参与自由行动。
- 用途：明石/不知火常驻商店。

### 4.3 商品表（M2 引入）

新增 `data/shop/goods.json`，以店主舰娘 id 为 key：

```json
{
  "akashi": {"name": "明石的商店", "goods": [{"id": "...", "name": "...", "price": 0, "type": "skin", "desc": "..."}]},
  "shiranui": {"name": "不知火的杂货铺", "goods": [{"id": "...", "name": "...", "price": 0, "type": "goods", "effect": "..."}]}
}
```

- 购买指令 `buy` 绑定店主舰娘（needs_target=True），店主名单硬编码于 `config/shop.py`。
- 明石的 skin 类商品 M2 先空（`"goods": []` 或占位），M4 填充——**数据驱动就是为了这个时间差**。
- 购买逻辑：检查金额 → 扣钱 → 按 `effect` 执行（`money` 类直接消费；`gift` 类进入礼物背包；`skin` 类进入玩家皮肤背包）。

### 4.4 礼物背包（M2 引入）

Player 新增运行时字段 `inventory: list[str]`（道具 id 列表）与 `skins: dict[str, list[str]]`（舰娘 id → 已购皮肤 id 列表，M4 用）：

- M2 实现 `inventory`（gift 类购买入包，送礼指令消耗）。
- M4 实现 `skins`。
- 两者都必须纳入 SaveManager 运行时字段清单（在对应里程碑计划中登记）。

### 4.5 relationship 推进与 EventManager（M3 引入）

- `relationship` 是已有 talent（0 陌生 / 1 友好 / 2 喜欢 / 3 爱 / 4 誓约），但当前无任何推进机制。
- M3 新增 `game_engine/events/__init__.py` + `game_engine/events/relationship.py`：
  - `relationship.py` 提供 `check_relationship_events(npc, player) -> list[str]`（推进事件文案）与 `relationship_conditions(npc) -> dict`（下一步解锁所需的好感/信赖阈值表）。
  - `world.event_manager` 挂到 `World`，`CommandManager.do_cmd()` 在指令成功返回非空结果后，若指令有目标 npc 则调用 `event_manager.check_npc_events(npc)`，事件文案追加到指令结果列表尾部。
- 推进条件（策划表，M3 可调）：
  - 友好：favor ≥ 500
  - 喜欢：favor ≥ 2000 且 trust ≥ 500
  - 爱：favor ≥ 5000 且 trust ≥ 2000（可告白）
  - 誓约：relationship = 爱 时执行 `誓约` 指令（需戒指道具 + favor ≥ 10000）
- 推进事件只升不降；同一阶段只触发一次（用 cflag 记 `relationship_event_{n}` 已触发）。

### 4.6 皮肤（M4 引入）

- 新增 `data/skins.json`：`{shipgirl_id: [{"id", "name", "price", "portrait", "avatar"}]}`。
- ShipGirl 新增运行时字段 `skin: str | None`（当前皮肤 id，None = 默认立绘）。
- 前端头像/立绘路径改为：有 skin 时用 `assets/skins/{shipgirl_id}/{skin_id}.webp`，否则回退 `assets/avatars|portraits/{name}.webp`。
- 口上差异：皮肤台词通过口上条件的 `skin` 字段实现（M1 扩展口上条件系统时预留）。
- `change_skin` 指令（needs_target=True，can：玩家拥有该皮肤）。

## 5. 各里程碑设计

### M0 存档读档

- 见 4.1。前端：
  - 主菜单"继续经营"→ `get_save_list()` → 槽位选择幕（含 day/时间/玩家名）→ `load_game` → `refresh()`。
  - 游戏内 Ex_COM 注册真 `save`/`load` 指令（移除 CommandManager 里的硬编码补丁）：
    - `save`：`get_cmd_options('save')` 返回 3 个槽位 → 执行后提示保存成功。
    - `load`：同样槽位选择 → 加载后 `refresh()`（清空选中态）。
- 测试设施：引入 `tests/` 目录 + 标准库 `unittest`（零新依赖），`python -m unittest discover` 运行。
- 顺手修复：`rub_the_belly` 的 get_line 动作名错误。

### M1 约会系统

- 新增指令 `date_invite`（约会，needs_target=True）：
  - can：relationship ≥ 1（友好）、favor ≥ 1000、玩家气力 > 0、NPC 未睡眠。
  - 执行：判定邀请成功（基础成功率 + favor 加成，失败则好感 -50 并结束）；成功则设置 `cflag['dating'] = True`、`cflag['following'] = True`，追加口上。
  - 约会中 flag 变化：`dating` 期间 NPC 不睡觉（update_positions 跳过其睡眠逻辑）、始终跟随玩家。
- 约会中专属指令 `date_action`（约会对话，需要「约会地点」选择）：get_cmd_options 返回当前区域的可约会节点；执行后推进时间、产生 source（happiness 为主）、好感结算。
- 新增指令 `end_date`（结束约会）：can 需要 `dating`；执行后 `dating = False`、`following = False`，按约会时长结算 mood（base['mood'] ± 值）。
- 跨天强制结束：`update_positions` 或 `settle_day` 中检测 `dating` 且时间进入深夜（hour ≥ 22 或 < 4）→ 自动结束约会并提示"她累了，结束了今天的约会"。
- 口上条件扩展：`_check_conditions` 支持 `min_relationship`/`max_relationship`/`is_dating`/`skin`（预留）。
- 新增台词：`date_invite`（同意/拒绝）、`date_action`、`end_date` 三个 action，4 只舰娘各写 2-3 条。

### M2 商店系统

- 地图：新增 `data/maps/shop.json` 区域（节点：柜台/货架区/休息室），`_regions.json` 注册 + `leave_time.json` 补全所有区域的互达时间。
- 数据：`data/characters/明石.json`、`data/characters/不知火.json`（含 `station` 字段指向商店柜台；明石 talent：维修商形象；两人台词只写买卖相关：`shop_greet`/`shop_buy`/`shop_leave`）。
- `NpcManager.update_positions()` 驻点分支（见 4.2）。
- 新增 `data/shop/goods.json`（明石空表、不知火日用品表）与 `config/shop.py`（店主 id 集合 + 购买流程函数）。
- 新增指令 `buy`（needs_target=True）：can = 目标是店主且玩家金钱 ≥ 商品最低价；执行弹 `get_cmd_options('buy')` 返回该店商品列表 → 扣钱、入包、提示。礼物入玩家 `inventory`。
- 新增指令 `give_gift`（送礼，needs_target=True）：can = 玩家 `inventory` 非空；`get_cmd_options` 返回背包礼物 → 消耗、好感/信赖结算（礼物按 price 分档：便宜 +5~10、中等 +15~25、贵重 +40~60）、口上 `gift` action。
- 新增指令 `shop_leave`（离开商店问候，needs_target=True，纯口上）。

### M3 告白/誓约

- EventManager（见 4.5）：favor 跨越阈值时推进 relationship 并触发事件文案；事件含：关系变化描述 + 对应口上 action（`relationship_event_{n}`）。
- 新增指令 `confess`（告白，needs_target=True）：can = relationship = 爱 且 favor ≥ 5000 且 trust ≥ 2000；执行：成功 → relationship = 爱（若未达爱则先推进）+ 专属告白口上 + favor 小幅下降（紧张）或直接进入"恋人"状态文案；失败条件设计：favor 低于阈值时拒绝并 favor -500。
- 新增指令 `marry`（誓约，needs_target=True）：can = relationship = 爱 且玩家 `inventory` 含 `ring`（誓约之戒，不知火卖 5000）且 favor ≥ 10000；执行：消耗戒指 → relationship = 誓约 → 触发誓约事件（专属口上 + 全属性 favor 上限变化 + `cflag['married'] = True`）。
- 誓约特权（M3 落地）：`cflag['married']` 为真时：每日自动+少量 favor；`hug` 等指令门槛减半；口上条件支持 `is_married`；状态栏头像旁显示"誓约"标记（前端）。
- 台词：`confess`（成功/失败）、`marry` 两个 action 4 只舰娘各写 2 条。

### M4 皮肤系统

- 数据：`data/skins.json` 每只舰娘 1-2 个皮肤；美术资源先占位（`frontend/assets/skins/{id}/{skin_id}.webp` 复制默认图）。
- 明石商品表填充 skin 条目（价格 2000-8000）。
- 购买流程：`buy` 指令对 `type: skin` 商品 → 写入玩家 `skins[npc.id]`。
- 新增指令 `change_skin`（needs_target=True）：can = `skin_id in player.skins[npc.id]`；执行切换 `npc.skin`，前端立绘/头像即时更新。
- 前端：头像排与立绘渲染函数改为按 `skin` 取图；立绘全屏层同样处理。
- 口上：`_check_conditions` 支持 `skin` 条件（M1 预留），给每只舰娘写 1 条换装后特殊台词。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 存档格式后期变更导致旧档失效 | 存档带 `version` 字段，M0 就定协议；字段增删走版本号 |
| 约会强制结束的边界情况（跨天/体力耗尽） | 结束判定集中放 `update_positions` 与 `settle_day`，两处共用同一函数 |
| 商店/皮肤工作量膨胀 | 明石 M2 空表、M4 填充；皮肤美术先占位 |
| 玩家数值膨胀导致攻略线失去挑战 | 送礼有分档阈值；告白/誓约条件在 M3 用配置表，随时可调 |
